# Experimental findings

This document summarizes the evidence I have collected so far for the investigation described in [REPORT.md](../REPORT.md). The results are limited to the specific artifacts and runs noted below.

I have approached this as a practical reproduction exercise: when I found a difference, I went back to the extraction logic, signatures, and available reports to understand it rather than assuming that the first explanation was correct. Some questions are still open, and I have marked those limitations explicitly.

## 2. Array-signature correction

While inspecting the signature logic, I found that the original implementation represented an array parameter with one `[` regardless of its dimensionality. I changed the experimental implementation to preserve the number of dimensions.

For `PDAnnotationMarkup.setInkList(float[][])`, the historical record used `[F`; my controlled experimental extraction recorded `[[F`.

The matching diagnostic also showed two methods newly matchable after the combined experimental changes:
- `PDAnnotationMarkup.setInkList`
- `ByteTrie.addPath`

This result is consistent with the descriptor correction helping these cases. However, the run also included the selector guard, so I have not established that the array fix alone caused both additional matches.

## 3. Selector null guard

The experimental `MockableSelector` includes a guard for invocations with no declaring-type reference. It returns `false` rather than raising a `NullPointerException`.

I consider this a separate behavioral change because it can affect which methods are classified as mockable. It should not be mixed up with the parameter-signature correction.

The experimental Maven build completed successfully. Compilation and packaging do not, by themselves, verify the full reproduction.

## 4. Matching results

| Unmatched methods | 556 | 554 |

The match count increased by two and the match rate increased by approximately 0.07 percentage points.

**My current interpretation:** The improvement is small, but it suggests that the descriptor issue may affect at least some matches. I am not treating this as a final causal conclusion because both experimental changes were present in the run.

## 5. Historical downstream reports

The repository's `pdfbox/README.md` and `pdfbox/execution/system-test-report.csv` contain different summaries.

The CSV `TOTAL` row reports 18,291 tests, 17,655 passing, 636 failing, 66 methods marked `well-tested`, and 45 marked `pseudo-tested`. These figures align with the PDFBox system-test results in Table IV of the paper.

These are existing historical artifacts. I have not described them as results newly generated by my current investigation. The separate README figures have unresolved provenance and may refer to another stage, configuration, or artifact version.

## 6. What I can conclude at this stage

1. The original signature logic I inspected did not preserve multidimensional-array depth.
2. My experimental extractor generated the expected `[[F` descriptor for the two-dimensional float-array example.
3. The combined experimental changes coincided with two additional matched methods.
4. The current comparison does not isolate the array-signature fix from the selector guard.
5. The historical downstream reports are evidence available in the repository, not proof of a newly reproduced downstream run.

These conclusions describe the current evidence. I expect some of them may become more precise after the next controlled experiment.

## 7. Next controlled experiment

I plan to use the same PDFBox source scope and inputs in a four-configuration ablation:

| Configuration | Array-signature fix | Null guard |
|---|---:|---:|
| A — baseline | No | No |
| B — signature only | Yes | No |
| C — guard only | No | Yes |
| D — combined | Yes | Yes |

For each run, I will record the source revision, command, source scope, extracted methods, eligible methods, matches, unmatched methods, duplicates, and match rate.

Before broad analysis, I also plan to add focused regression tests for one-, two-, and three-dimensional primitive arrays and one- and two-dimensional object arrays. The selector's null-declaring-type behavior should be tested independently.
